复核发现的两个新问题（0.10.2）：N1 详情区显示"0 字节"、N2 测试永远不会失败

N1 —— 结构体详情的字节数恒为 0

    根因不是"数据流里没有 elemBytes"这么简单，中间还隔了一层：
      simview.ts:620 用 {...x} 展开，catalog 【本来就带】elemBytes；
      但 renderVariables 传给 renderStructDetail 的是它自己拼的
      picked 对象（simview.js:546），那里只带
      name/dims/kind/isStatic/total/manual —— elemBytes 被丢掉了。
    于是 v.elemBytes 恒 undefined，兜底成 0，
    用户点开任意结构体都看到「整体大小（0 字节）」。

    ★ 一个看起来像 bug 的错误数字，比不显示更糟。

    修法（用户选定）：【不显示字节数】。理由是它本来就是冗余的 ——
    C 侧把 SCUT_T_STRUCT 渲染成 "<104B>"、指针渲染成 "%p" 地址，
    大小已经在上面的值栏里了，详情区再说一遍既冗余又可能是错的。
    改成只说明"不解析成员表"+ 下一步该怎么做。

    ★ 顺带修了一处我自己写错的 API 名：SCUT_WATCH_SCALAR 这个符号
      并不存在（真实名字是 SCUT_Watch），照抄会让用户去搜一个不存在的东西。

N2 —— test_webview_js.py 的 check() 参数顺序反了，这测试永远不会失败

    签名是 check(cond, msg, extra='')，而 4 个调用点全写成
    check('描述文字', 条件)：
      cond 收到描述字符串（恒真）→ 永远走 if 分支
      msg  收到布尔值            → 所以输出是 "[OK] False"
      failures 一次都不追加      → exit 恒为 0

    讽刺：上一个提交的说明里刚写过"第一版我在桩里 catch，测试没报错
    看起来像有兜底 —— 假绿色"这个教训，在 check() 这层又重犯了。
    这也印证了复核者自己的一条：批量断言的输出必须独立复核。

    ★ 修好参数顺序后，这条测试立刻变红并指出另一个真问题：
      really_threw 原本要求 'boom-from-stub' 出现在 stdout，
      而【修好之后】异常被 simview.js 自己的 try/catch 吃掉，
      永远打不出来 —— 拿它当判据会造成"修好后反而红"，
      于是测试逼着人把兜底拆掉才能变绿。改用 TOUCHED 判据
      （由 textContent 的 setter 置位，只有 renderVariables
      真的执行到那一行才为 true）。

    ★★ 验证方式：注入缺陷，证明测试真的会红 ★★
      ① 把 renderStructDetail 改名（等价于"从未定义"）
         → [FAIL] 点击「展开字段」不抛 ReferenceError
           driver: CLICK_CAUGHT "ReferenceError: renderStructDetail is not defined"
      ② 拆掉 vars 分支的 try/catch
         → [FAIL] 异常没有逃出 message 处理器
      两次都 exit 1，且都点名具体缺陷。
      这才是"它在守"的证据；"跑绿了"不是。

run_all_tests.py：symbols 的 primary 从 gcc 换成 clang

    ★★ 这是本轮最有价值的一条结构性修正 ★★
    以前 primary=gcc、clang 走 --also，看上去"两个都测了"。
    但插件【分发】的工具链是 llvm-mingw（clang），
    而 B2（数组 typedef 维度被覆盖）恰恰【只在 clang 上触发】
    —— gcc 会把 typedef 拍平，旧写法在 gcc 上一直是"对的"。
    于是 B2 在 primary 里一直绿，只有 --also 那一轮才红，
    而 --also 的结果很容易被当成"次要/可选"。

    这就是"测试环境与分发环境不一致"——
    一个结构性原因，胜过"没人触发"这种解释。
    现在 primary 是 clang（分发用的那个），gcc 保留为 --also
    （scut_symbols.py 的跨工具链承诺仍然要验）。
