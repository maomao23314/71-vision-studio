## 一、三层结构与依赖方向

```
┌─────────────────────────────────────────────┐
│  ① 插件显示层   extension/  (TypeScript)      │
│     只管 UI：设置、变量面板、图像显示、日志     │
└───────────────┬─────────────────────────────┘
                │  设置(scut_project.json) + stdin/stdout JSON 协议
                ▼
┌─────────────────────────────────────────────┐
│  ② 仿真环境层   tools/ + core/ + bind/ + backend/ │
│     提供输入图、收集变量、合成绘制、计时、喂图集  │
└───────────────┬─────────────────────────────┘
                │  自动生成的接线单元 (glue) + 纯 C 调用
                ▼
┌─────────────────────────────────────────────┐
│  ③ 用户代码     code/*.c                     │
│     只有算法。不写注册、不写 main              │
│     （可选的绘图/日志调用除外，见下）          │
└─────────────────────────────────────────────┘
```

**依赖是单向的**：①→②→③。用户代码不知道 ① 和 ② 存在。

> ★ 上面那句"不依赖仿真环境"要读准（2026-10-11 补）：用户代码里
> **可以**出现 `SCUT_Draw*` / `SCUT_Log`，它们属于**主机侧调试设施** ——
> 移植到车上时给空实现、或直接删掉调用即可（见 `scut_sdk.h` 的分区说明）。
> 真正不许出现的是：注册宏、`main`、仿真专用缓冲副本、把结果搬进
> "输出图"的循环 —— 那些全部由环境侧接管了。

## 二、关键约束（为什么这么设计）

### 2.1 用户代码必须能直接拷上单片机

这是**第一约束**，其它设计都要给它让路。具体体现：

| 用户代码里不该有 | 谁来做 |
|---|---|
| `main()` | 后端（`backends/headless/`） |
| `SCUT_INIT/FRAME/POST` 注册 | 构建时生成的 glue 单元 |
| 仿真专用缓冲副本 | 环境提供全局 `mt9v03x_image` |
| 把结果搬进"输出图"的循环 | 构建时生成的 glue 单元 |

**允许保留**（用户明确认可的"无关紧要的胶水"，移植时不调用即可）：
- `SCUT_DrawPoint/DrawLine/DrawRect/DrawText` —— 画调试标注
- `SCUT_Log` —— 打调试日志

理由：车上本来就有 IPS 屏和串口，这两类调用的**实现在车载工程里自然存在**，
所以留在算法文件里不算"仿真依赖"。

### 2.2 三个钩子函数必须是非 static 的

glue 单元是**独立编译单元**，只能调用有外部链接的函数。所以：

```c
void my_init(void);        /* ← 必须非 static */
void image_process(void);  /* ← 必须非 static */
void my_draw(void);        /* ← 必须非 static */
```

这**不是限制**：车上 `main()` 要调用它们，本来就必须非 static。
所以插件要求的签名与车载工程的要求**完全一致**——这正是可移植性的体现。

### 2.3 图像尺寸是编译期常量，改不了

C 语言里 `uint8_t buf[SCUT_IMAGE_H][SCUT_IMAGE_W]` 的尺寸必须是编译期常量。
用户算法里到处是这种声明，所以**尺寸契约必须存在**。

结论：尺寸放在 `scut_project.json` 里由 UI 编辑，**构建时生成编译期头文件**
（`.scut/gen/scut_config.h`）。用户不再手写 `config.h`，但契约依然存在。
这是"配置进 UI"与"语言硬约束"的唯一调和方式。

### 2.4 输出图必须深拷贝

用户算法把结果写进**它自己的**数组（如 `binary_image`）。
环境需要拿到结果图，做法是 glue 里逐个像素深拷贝。

**为什么不能浅拷贝/换指针**：
算法里存在**逆透视指针表**（`PerImg_ip[H][W]`，元素是 `uint8_t*`），
它指向输入图的像素。若把指针表的目标换掉，表里所有指针立刻悬空。
所以输入图必须是**长期稳定**的一块内存，且只能按值拷贝内容。

### 2.5 输入图由环境提供，且地址恒定

- 环境在 `bind/scut_bind.c` 里定义 `mt9v03x_image[H][W]`（沿用逐飞/车载惯例命名）。
- 后端每帧把测试图解码进这块内存。**地址永不变**。
- 用户算法直接读写 `mt9v03x_image`，与车载工程一致。
- 逆透视指针表建表时指向它，**天然长期有效**——不再需要同步副本。

> 旧实现里用户代码自己声明 `static mt9v03x_image[H][W]`，再加一层
> `SCUT_GetInputImage()` 拷贝、以及一份 `mt9v03x_image_local` 给指针表用，
> 一共三份拷贝。重构后是**一份**。

## 三、运行时数据流

```
每帧：
  后端解码测试图 → mt9v03x_image          （地址恒定，指针表有效）
  ↓
  INIT 阶段：glue 调 scut_env_init()  →  用户 init 函数们      （不计时）
  ↓
  PROCESS：glue 调 scut_env_frame()   →  用户处理函数们        （★ 计时）
  ↓
  DRAW：   glue 调 scut_env_draw()                            （不计入处理时间）
             ├─ 深拷贝用户结果数组 → 环境输出图
             └─ 用户 post 函数们（画线 / 打日志）
  ↓
  合成 overlay → 输出图，清空 overlay
  ↓
  frame sink：后端把输出图与变量快照写成 JSON + PPM → 插件
```

> **更正（2026-10-10）**：这里原有一行「REPORT：日志门控打开，收集日志行」。
> REPORT 阶段**已被删除** —— 旧实现把绘制注册成 REPORT 角色，而 REPORT 排在
> 合成**之后**，于是合成拿到的是一块还没被写过的覆盖层，直接导致
> 「标注全部静默消失」。现在只有 PROCESS / DRAW / IDLE 三个阶段，
> 见 `core/src/scut_sched.c`。文档比代码多写了一个阶段，也是 bug 的一种。

### 变量收集（两条路径，合并成一份清单）

1. **编译期自动发现**：探针 `.o` 的 DWARF → `scut_symbols.py` → `*.vars.json`
   → 生成一个 `#include 用户源码` 的包装单元，在构造函数里 `SCUT_Watch()` 注册。
   （`#include` 是唯一能触及 `static` 变量的办法。）
2. **运行期手动注册**：`SCUT_Watch` 显式调用（结构体成员等 DWARF 不透明的情况）。
   构建后用 `exe --list-vars` 把运行期注册表补进清单。

清单里区分 `manual`（主动暴露，面板排前面并高亮）与自动捕获（灰色）。
判据：**运行期注册表里有、编译期清单里没有** → manual。

## 四、配置：`scut_project.json`

单一真值来源，由插件自己的配置面板编辑，放在工程根。

```jsonc
{
  "image":  { "width": 188, "height": 120 },
  "hooks":  {                       // 三个钩子，每项是函数名数组，按顺序调用
    "init":  ["ImagePerspective_Init", "my_init"],
    "frame": ["image_process"],
    "post":  ["my_draw", "my_report"]
  },
  "output": { "array": "binary_image" },   // 结果图来源数组，空则不做深拷贝
  "pic":    { "dir": "pic/1", "ext": ".bmp", "start": 1 }
}
```

构建时由它生成 `.scut/gen/scut_config.h`（编译期尺寸）与 `.scut/gen/scut_env_glue.c`。

**为什么不用 `config.h`**：用户会乱改、会把算法参数塞进去、会忘记同步。
JSON 由 UI 管，生成物带 "DO NOT EDIT" 头，职责清晰。

### 4.1 0.9.4 起：插件的【全部】设置都在这一个文件里

在此之前，值与可以去处有两处（VS Code 的 `settings.json` 与本文件），
并且互相覆盖。结果是三重坑：

| 坑 | 现象 |
| --- | --- |
| 嵌套 object 分组不注册内层键 | `contributes.configuration` 里写 `"scut71.toolchain": {"type":"object","properties":{...}}`，VS Code 只注册【顶层键】，于是 `cfg.get('path')` 永远读不到；`cfg.update('path')` 直接抛「没有注册配置 scut71.toolchain.path」 |
| 两个真值互相压 | `project.ts` 里 `fromSettings ?? fromProjectConfig` —— 工程 JSON 里配的图集目录根本不生效，且不报错 |
| 死界面 | `view.showTiming/showLog/…` 四项全项目没人读，用户勾了没效果，反过来怀疑自己用错 |

现在：

- **不再有 `contributes.configuration`**。配置不经过 VS Code 那套机制，
  也就没有"注册不上"这种失败模式。
- 编辑入口是插件自己的 Webview 面板（`settingsview.ts`），
  字段表集中在 `configfields.ts`，读写走 `projectconfig.ts`。
- **包含工具链**（`toolchain.path`）—— 用户明确要求"所有配置项统一进去"。
  代价要记账：工具链是【本机】环境，跟着工程走意味着换机器要重填一次，
  而且【没打开工程时读不到】（此时等同没配置，继续走
  `SCUT71_TOOLCHAIN` 环境变量 → PATH → 弹窗询问）。

> 注：早期注释写过「VS Code 用户设置里只留本机环境类选项」。
> 这条在新版【已作废】—— 保留两个真值被证明代价更高。
> 若日后要恢复"按机器的全局工具链"，用环境变量即可，不要再把配置拆成两处。

### 4.2 必须同时存在于 `tools/scut_build.py` 的 `DEFAULT_CONFIG`

两者是同一份数据的两个视图（TypeScript 侧 `ProjectConfig` 接口 vs Python 侧默认值），
**字段名必须逐字一致**，否则插件写的字段脚本读不到，或反过来。
`tests/test_extension_settings.py` 用一条断言守着这件事。

### 4.3 图像格式是运行期参数，不需要重编译

`pic.ext` 支持**逗号分隔多个后缀**（如 `.png,.bmp`），仿真会逐一尝试，
所以同一目录里混着多种格式也能跑；`pic.dir`、运行次数同理。
这些只作为命令行参数传给仿真程序，**不会写进生成的 C 代码**。

已知边界：解码器支持 BMP（24/8 位）与 PNG（8 位灰度/真彩/调色板、非交织），
**JPEG 需先转成上述格式**。

### 4.4 构建脚本的 Python 解释器可由用户指定

`toolchain.pythonPath` —— 跑 `scut_build.py` / `scut_symbols.py` 用的解释器。

**只需要 3.7+，零第三方库依赖**（两个脚本的 import 全是标准库：
argparse / json / re / subprocess / typing / concurrent.futures …），
所以 conda、python.org、Windows 商店版任选其一都行。

★ 为什么要有这个配置（用户实测踩到的）★
机器上装了多个 Python 时自动探测会挑错：

```
py -3   → 反查到 Python36-32 注册的 3.6.2
PATH    → python 也是 3.6
真正能用的 3.12（conda）既不在 PATH 上、py 启动器也不知道
→ 探测链全断，而报错却让用户"再去装一个 Python"
```

优先级：`toolchain.pythonPath` → `SCUT71_PYTHON` 环境变量
→ 工具链自带 → `py -3` → PATH。
前两者若指向 3.6，**不自动换候选**（用户明确指定了路径，插件替他换等于自作主张），
但会把「这个解释器跑不动脚本」讲清楚并引导改配置。

### 4.5 ▶ 面向他人的默认值（重要）

本机特定的路径一概**不得写进代码或配置样例**：

- 不硬编码任何盘符/用户目录（`mem-safety` 测试守住这条）
- 不以开发机的安装布局作为待探测目标
- 默认配置的语义是"自动探测"，不是"照抄我的机器"

用户拿到插件后，配置面板里每一项都能改；探测失败时的提示要说清
「去哪里改」，而不是「装更多东西」。

## 五、绘制与日志的落地（防止"静默消失"）

- 绘制写进**覆盖层**（`u32` 数组），不是直接写灰度图。
- 调度器在 DRAW 之后**先合成、再清空**覆盖层。
- 合成由**调度器**做，不由后端做：否则每个后端都得自己记得合成一次，
  漏一个后端 → 标注静默消失（旧环境栽过）。
- 日志走 C 侧环形缓冲，后端每帧抽干并走 **stderr**，保持 stdout 是纯 JSON 通道。

## 六、已知边界（不隐瞒）

1. **中文标注不支持**：内置 8×8 ASCII 字库，非 ASCII 画占位方框。
2. **JPEG 不支持**：BMP + PNG（8 位、非交织、自带 inflate）。
3. **结构体字段名不可知**：DWARF 成员表未解析，只能整体报大小。
   需要看具体字段时用 `SCUT_Watch` 手动注册该成员。
4. **从未被引用的 static 变量发现不了**：被编译器删掉了，与调试器行为一致。
5. **仿真 ≠ 真机性能**：默认 `-O0` 便于调试；看优化后耗时用 release 模式。
6. **阶段门控是防呆不是防护**：C 语言无法阻止直接访问全局数组。

## 七、第九轮的修正（2026-10-11）

> 本节记录本轮修掉的**与架构相关**的问题。
> 起因是一轮外部评审，结论见 `docs/代码评审报告_20261011.md`（该文件不进 git）。

### 7.1 构建脚本的图集目录曾经是"第二个真值"

`Project.__init__`（`tools/scut_build.py`）构造时把 `pic_dir` 写死成 `<root>/pic`，
而配置是**之后**才由 `load_project_config()` 读出来的 —— 构造顺序在前，
所以配置里的 `pic.dir` **从来没有生效过**。

后果不只是"没起作用"，而是**主动误导**：用户在面板里把图集设成 `pic/3`，
仿真会正确地用 `pic/3`（后端读得到），但构建时打印

> 警告: 工程里没有 pic/ 目录，仿真将没有测试图可读。

而画面根本不会黑。用户于是去建一个并不需要的 `pic/`。

**这正是 §4.1「配置只有一个真值」要消灭的缺陷，却在同一文件里重新出现。**
现在由新增的 `apply_pic_dir(proj, cfg)` 在配置读出来后立刻回写，
两个调用点（`do_build` 与 doctor）各自调一次。

> ★ 教训：**「唯一真值」不是把值集中到一个文件就完事，
> 而是必须保证每一个消费者都真的去读它。** 有一个消费者还在读硬编码，
> 真值就不唯一 —— 而且这种漏网比"两处都读配置"更难发现，
> 因为漏网的那一处看起来"一直就是那样工作的"。

### 7.2 「运行」与「调试」必须拿到同一组图集参数

`debug.ts` 曾经写死 `args: ['--frames', '1']`，完全不补 `--pic` / `--ext` / `--frame`；
而 `simsession.ts` 启动会话时会自行补上。于是配了 `pic.dir = "pic/3"` 的工程
**运行用 pic/3、F5 调试用编译期默认值**（或全黑图），
而两个入口"看起来"是同一件事。

现在两边都调 **`extension/src/simargs.ts`** —— 一处实现、两处使用。

该文件是**纯函数、且不 import `vscode`**，因此：
- 两条路径不可能再拼出不同的值（结构上排除，不是靠约定）；
- 它可以在普通 Node 进程里被直接单测
  （见 `tests/extension_smoke.js` 第 7 组，16 条断言）。

> 这与 §2.4/§五 里"合成必须由调度器做、两个缓冲显式传参"是同一个思路：
> **消灭"两处各自知道同一件事"**。

### 7.3 生成的契约头里的文案属于"长期存在物"

`.scut/gen/scut_config.h` 会被写进**每一个用户工程**。它原先写着

> 要改这些值，请用 VS Code 设置界面（搜索 "SCUT-71"）

而 0.9.4 起配置已不在 VS Code 设置里。**这句错话的存续时间比任何一份
README 都长**，因为它是落盘在用户工程里的。

**规范**：凡是要写进用户工程/生成物的字符串，一律指向
「插件配置面板」或直接点名 `scut_project.json`，
**不得**再出现与具体实现绑定的说法（"设置界面"、"settings.json"）。

### 7.4 命令面板不再被整体屏蔽

`extension/package.json` 曾有 `"menus": { "commandPalette": [] }`。
它的语义是"对所有命令应用空规则集"，即**注册的命令全部从命令面板移除** ——
14 个命令里 7 个（含「新建仿真工程」「环境自检」）因此搜不到，
而 README 的第一步正是叫用户去命令面板执行它们。

那个空列表是"GUI 注册重构"时期的产物（`git log -S` 可查到它是
`checkpoint before GUI-registration rework`）。现已删除，回到 VS Code 默认行为。

**为什么不给那 7 个命令补 UI 入口**：它们当中只有「配置本工程」真正属于配置，
其余 6 个（新建工程 / 自检 / 看日志 / 开视图 / 选变量 / 开设置）不是配置项，
塞进配置页很别扭。而**命令面板本身就是 VS Code 为低频命令准备的入口** ——
低频不等于需要重新发明一个入口。

### 7.5 本轮**没有**改的（记账）

死代码清理、`log_enabled`/`SCUT_PROCESS_REPEAT` 等"半死配置"的取舍、
`SCUT_FRAME_ERR_NOMEM`、5.1/5.2 节那批过时阶段注释、
Python 版本闸门 3.7 vs 3.8、`run_cmd` 超时、`_core_fingerprint` 的编译器身份 ——
都留到第二批。完整清单见 `docs/第九轮修复计划书.md` 第六节。

## 八、第十轮的清理（2026-10-11）

> 第二轮。只做**死代码、半死配置、过时注释**——不改任何对外行为。
> `tests/test_cleanup.py` 为这一轮新增的 78 条断言守着（双向：防回潮 + 防误删）。

### 8.1 删除清单（都是"零调用"确认过的）

| 删掉的东西 | 位置 | 为什么它必须消失 |
|---|---|---|
| `scut_registry_internal.h` | 整文件 | 它定义的 `SCUT_REGISTER` 宏体调用 `SCUT_Register` —— **该符号全树不存在**，一用就链接失败；而真正在用的宏是 `scut_registry.h` 的 `ENV_REGISTER`。且只有 `scut_registry.c` include 它，而后者不需要它 |
| `scut_input_violations` / `scut_input_reset_violations` | `scut_input.c` + `scut_internal.h` | 零调用。注释说"只用于一次性提示"，但一次性提示由 `if (s_violations == 1)` **自己**实现，重置函数纯属多余 |
| `sink_begin` / `sink_end` / `sink_us` | `scut_sched.c` | 算完之后一句 `(void)sink_us` 丢掉。`frame_us` 早在 sink 之前就读表发布了，sink 按定义不该计入任何指标 |
| `SCUT_GetImageWidth` / `SCUT_GetImageHeight` | `scut_draw.c` + `.h` | 实现与 `SCUT_GetOutputWidth/Height` **逐字相同**（同一组 `s_w`/`s_h`），名字却暗示"输入图尺寸" —— 一个会骗人的 API。需要输入图尺寸请用 `SCUT_GetInputImage` |
| `#ifdef SCUT_PROCESS_REPEAT` 整块 | `bind/scut_bind.c` | 那个宏**从来没有任何地方生成**（生成的 `scut_config.h` 只发 W/H 与输入数组名），`#ifdef` 恒假，永远走 `#else` |
| `write_config_shim()` | `tools/scut_build.py` | 零调用，而它的 docstring 写着"见调用点"—— 没有调用点 |
| `latin-1` 解码候选 | `tools/scut_build.py` `decode_output` | `latin-1` **永远不会失败**，所以列表末尾的兜底是不可达死代码；更糟的是 `gbk` 会**静默乱码**而不是抛异常，导致 UTF-8 中文诊断走不到正确分支。改成"先严格 UTF-8，失败才 GBK" |

### 8.2 半死配置：要么能设，要么删掉

`scut_run_config_t` 的三个字段里，只有 `repeat` 有运行期入口
（`scut_sched_set_repeat`，`b<N>` 测速命令在用）。
`log_enabled` / `draw_enabled` 只有 `scut_bind_apply()` 写死成 1，
**全树没有任何地方能改它们** —— 于是 `scut_sched.c` 里两个 `if` 恒走真分支。

**决策：补 setter，而不是删字段**（见 `scut_sched.h` 的 `scut_sched_set_log_enabled`
/ `scut_sched_set_draw_enabled`）。理由：这两个开关有真实用途
（关日志避免压测刷屏、关绘制做纯算法基准），删掉等于承认"永远不需要"；
而补齐之后，**结构体里能赋值的东西就都能改**，"半死"状态消失。

> ★ 判据（可推广）：**一个配置字段如果没有任何消费者能改变它，
>   它就不该存在；如果它有用途但没入口，就该补入口。**
>   "留着但改不了"是最坏的一种 —— 读代码的人会以为能配。

### 8.3 错误归因：内存不足 ≠ 格式不支持

`scut_frame.c` 里四处 `malloc`/`realloc` 失败原先都返回
`SCUT_FRAME_ERR_PNG_FORMAT`（注释写着"内存不足：按「数据无效」归因"）。
但该码的文案是"PNG 色深/颜色类型/交织方式不在支持范围内"，
宿主据此引导用户**"把图转成 8 位灰度 PNG"** ——
用户拿着一张好图，却被指去做一件永远解决不了问题的事。

新增 `SCUT_FRAME_ERR_NOMEM (-17)`，四处全部改用它，并配独立文案：

> 内存不足：这张图太大，分配解码缓冲失败了。**图片本身没有问题。**
> 下一步：换成尺寸小一些的测试图，或关掉其它占用内存的程序后重试。

这回到 `scut_frame.h` 自己定的规矩：**一条一类具体原因一个码**。
"重转一次格式"和"关掉别的程序"是完全不同的下一步，共用一个码就必然指错方向。

### 8.4 过时阶段注释：三个不存在的阶段

`PRE_FRAME` / `POST_FRAME` / `REPORT` 早已从阶段模型里删除
（现役只有 `IDLE` / `PROCESS` / `DRAW`，见 `scut_internal.h`），
但多处注释仍在描述它们，其中两处尤其有害：

1. **`scut_headless_main.c` 把错误的帧内顺序写成了"契约"**：
   原文是 `PRE_FRAME → PROCESS → POST_FRAME → sink → DRAW → REPORT`，
   而真实顺序是 `PROCESS → 默认底图 → DRAW → 合成 → 清空 → sink` ——
   **sink 的位置也写反了**。把错误顺序冠以"顺序本身是契约"，
   后来者会照着它去"修正"代码。
2. **`scut_draw.c` 说"覆盖层由 frame 模块合成"**，而合成早已移到调度器
   （`frame` 那份缓冲 2026-10-10 已整块删除）。

以上均改为指向 `scut_internal.h` 的阶段枚举与 `scut_sched.c` 的 `run_one_frame`，
并在原地保留"曾经写错什么"的记录。

### 8.5 健壮性：三个"迟早会咬人"的地方

| 问题 | 修法 |
|---|---|
| **外部命令没有超时** | `run_cmd` 加 `timeout`（构建 300s / 版本探测 20s 两档）。原先 `_probe_version` 的 `timeout` 形参**从未使用**，而工具链探测要连试最多 8 个 objdump 路径 —— 任何一个挂住，构建就**永久挂起**，用户只看到"编译转圈" |
| **核心库指纹不含编译器身份** | `_core_fingerprint` 拼入 `tc.cc` 绝对路径 + `cc_version`。否则换工具链（或 msvcrt↔ucrt）后源码没变 → 指纹没变 → **复用旧 ABI 的 `.a`**，得到一堆指不到病根的链接错误 —— 与 `sync-sdk.js` 痛斥的"分发预编译库"是同一类事故，只是发生在本地增量缓存 |
| **`--jobs` 无上限** | 注释写"上限 16"，但夹取只作用于**自动推导的默认值**。`--jobs 9999` 会真的起 9999 个线程、每个拉一个 clang，机器直接假死。现在 `JOBS_MAX` 常量同时约束两处 |

另外把 `scut_symbols.py` 一直支持、但 `scut_build.py` **从来不传**的
`--exclude` / `--max-elems` 接通了（并补了同名 CLI 选项与中文帮助）。
一个"实现了却没人能调到"的开关，会让人以为构建侧已经在用它。

### 8.6 Python 版本下限：统一到 3.7，并说真话

四个文件曾给出两个互斥的下限（插件侧 3.7、脚本 3.8）。实测
`scut_build.py:95` 声称的 3.8 理由（"f-string 调试、typing 简化写法"）
**在代码里根本不存在**：零个 f-string 调试说明符、零个 PEP 585/604 写法。
真正的下限来自 `from __future__ import annotations` —— 那是 **3.7** 的特性。

统一为 **3.7**，并补上一件更要紧的事：**闸门失败时也输出一份 JSON**。
原先直接 `raise SystemExit(2)` 不吐 JSON，而插件只在看到 `/SyntaxError/`
时才换解释器重试 —— 于是版本刚好卡在闸门下沿时，
用户看到的是笼统的"无法运行构建脚本"，真实原因（"你的 Python 太老"）
根本没传到他眼前。
