### 排查结论（动手之前）

**三层现状（架构本身是对的，符合设计理念）**

```
① 插件显示层   extension/ (TS + webview)      只管 UI
        ↕ scut_project.json + stdin/stdout JSON 协议
② 仿真环境层   tools/scut_build.py + core/ + bind/ + backends/headless/
        ↕ 构建时生成的接线单元 scut_env_glue.c
③ 用户代码     code/*.c                        只有算法
```

**问题 1 根因（已确认）**

- `code/camera.c` **当前编译不过**（用 SDK 脚本实测）：
  - 第 1958 行 `camera_draw()` 用了 `image_used`（小写），该标识符不存在；正确名字是 `ImageUsed`（`Perspective.h` 里的 `#define ImageUsed *PerImg_ip`）。
  - `scut_compute_otsu_probe()` 在文件开头声明、在 `camera_report()` 里调用，**但没有定义** → 即使修好上一处，链接期也会报未定义。
  - 连带：探针编译失败 → 自动符号发现拿不到 `binary_image` → 构建脚本又报「结果图数组名在 code/ 里找不到」。
- 用户说"目前也能跑起来"= 跑的是 `.scut/bin/scut_sim.exe` 这个**旧的构建产物**，源码本身已经坏了。
- "图片明显不对"还有一层：`binary_image` 里存的是**类别值**（0/1/2/3/4/6），直接当灰度显示几乎全黑；4bb7 是把它按类别映射成颜色显示的（`screen.c` 的 `my_show_line_only`），默认视图则是**逆透视后的图 `ImageUsed` + 边线/中线标注**（`my_show_perspective_image`）。

**问题 2 根因（已确认）**

- `media/simview.css` 里 `#vars-section` 是 `display:flex; overflow:hidden`，但它的子元素 `#vars-body` **没有** `flex:1 1 auto; min-height:0`，`#vars-list` 的 `overflow-y:auto` 因为父级不受限而永远撑成内容高 → 超出部分被 `overflow:hidden` 裁掉，**滚不动**。

**问题 3 根因（已确认）**

- 后端把用户日志发到 **stderr**，行首带 `[LOG] `（`backends/headless/scut_headless_main.c` 第 2118 行）。
- 扩展 `simsession.ts` 的 `onStderr` 又在前面加了个 `[仿真] `，变成 `[仿真] [LOG] …`。
- `simview.ts` 的 `pushLog()` 用 `line.startsWith('[LOG] ')` 判断是不是用户日志 —— 前缀被 `[仿真] ` 挡住，**判定永远为假**，于是用户日志被写进「SCUT-71 构建」输出通道，而**专门的「SCUT-71 运行日志」通道和侧边栏「日志」折叠区永远为空**。
- 侧边栏 HTML 里其实有 `#log-section` 折叠块，webview 也处理 `type:'log'` 消息，但**宿主从来没往 webview 发过 `log` 消息** → 那块是死的。

**问题 4 根因（已确认）**

- `media/simview.js` 里**勾选区**已经区分了 `manual`（主动暴露，蓝色、排前面、带分组标题），但**查看区** `renderVariables()` 构造 `picked` 时把 `manual` 字段丢掉了，所以查看区所有变量长得一样。

**问题 5 根因（已确认）**

- `tools/scut_build.py` 其实已经做到"用户代码恒 `-g -O0`"（`user_flags`），真正受 `--mode` 影响的只有**环境自身**（bind 单元、核心库、后端：`env_flags` debug=`-g -O0` / release=`-O2 -DNDEBUG`）。
- 也就是说这个设置项唯一的用途是"环境库要不要优化"，而这**不该让用户选**。用户要求：C 用户代码恒 O0，其余部分可以优化。

**问题 6 根因（已确认链路可用，问题在接线）**

- 用 `tests/dap_smoke.js` 实测：`lldb-dap` + 当前 `scut_sim.exe` 的完整 DAP 会话 **6/6 通过** → 适配器与程序本身没问题。
- 插件侧疑点：
  - `package.json` 把 **`F5` 绑给了 `scut71.run`**（`when: view == scut71.simview`）。用户十有八九是**在仿真视图里**按 F5，于是触发"运行 N 帧"而不是"开始调试"，看起来就是"调试打不开"。
  - 没有独立的"调试"命令/按钮，入口只有 F5，且被上面的键位抢走。
  - 装了 `ms-vscode.cpptools`（`cppdbg`）也认 C 文件，无 `launch.json` 时 F5 可能弹调试器选择，用户容易走错。

### 问题 1：主动注册的变量看不见

**结论：两个独立的缺陷叠在一起，只修任何一个都仍然看不见。**

#### 缺陷 A：判据是错的（宿主侧）

原来的做法是"运行期注册表里的名字 − 编译期 DWARF 能看到的变量"= 手动变量。
实测证明这个判据**恒等于空集**：

- 运行期注册表 42 个，编译期 DWARF 清单 42 个，**交集也是 42**（差集 = 0）。

为什么？因为自动发现的包装单元会把用户源码 `#include` 进来，
于是用户写的**每一个** `SCUT_WATCH_SCALAR` 都同时出现在两边 —— 两边都覆盖它，差集自然为空。

更关键的是：用户手写注册的最常见形式是**结构体成员**
（`SCUT_WATCH_SCALAR("cam_err", &m7_0_data.cam_err, SCUT_T_F32)`），
而**结构体成员在 DWARF 里没有独立的变量条目** —— 实测那 7 个手写变量一个都不在 DWARF 清单里
（单 `camera.c` 只产出 32 个 DWARF 变量，合并后 42 个）。
所以"只给 DWARF 变量打标记"这个做法注定漏掉全部 7 个。

**改法：改成扫源码。**

- `tools/scut_symbols.py`：新增 `scan_manual_watches(src)`，正则匹配手写的
  `SCUT_Watch("名字", …)` / `SCUT_WATCH_SCALAR("名字", …)`，**只去注释、不去字符串字面量**
  （要抓的恰恰就是那个字符串）。名字写进清单**顶层**的 `manualWatches`。
- `tools/scut_build.py::merge_manifests`：**跨所有 TU 求并集**。
  只看单个文件的话，注册写在哪个文件会决定这个功能有没有效 —— 结果取决于无关因素。
- `extension/src/build.ts`：把运行期独有的条目（`extra`，也就是 DWARF 覆盖不到的那批）
  按 `manualWatches` 标记，而不是一律当自动捕获。
- **排序**：手动项要先挑出来置顶（`[...manual, ...extra.filter(manual), ...auto, ...extra.filter(自动)]`）。
  只拼一次的话，那 7 个结构体成员会落到列表最后 —— 而它们恰恰最该置顶。

#### 缺陷 B：注册函数压根没被调用（工程侧）

`camera_watch()` 里写着那 7 行注册，但这个函数**从来没被执行过**：
既不在 `scut_project.json` 的 hooks 里，也不在生成的接线单元里 —— 全仓库只有"定义"和"声明"，没有调用。
所以那些变量从来没有被注册进运行期注册表（实测注册表 42 个，不含这 7 个；挂上钩子后变成 49 个）。

### ★ 丢线的真正根因：`black_thres=200`（不是移植 bug）

移植完成后算法本身已经正确，但**仍然丢线**。这次做了干净的 A/B
（每种取值都重新编译，只让 `black_thres` 一个变量不同，跑全部 63 张图）：

| `black_thres` | 全跟踪（tracked=2） | 完全丢线（tracked=0） |
|---|---|---|
| **200**（4bb7 `flash.c:19` 原值） | **0 / 63** | **42 / 63** |
| **10**（参考工程 `camera.h:73` 的值） | **48 / 63** | **2 / 63** |

机理在 `camera.c` 的 `ratio_x_judge()`：
`tmp = RATIO_X_THRES * (left + right)`，`tmp < BLACK_THRES` 判为"黑、无边界"。
`black_thres=200` 等价于要求 **左右梯度之和 > 200**，即**平均亮度 > 100**。
实测这 63 张图全图均值只有 38~50、下半图 28~44 ——
**整条路都被判成黑色**，`get_start_point` 自然找不到起点，于是丢线。

**结论：这是调参，不是移植缺陷。** 4bb7 的 200 是给"明亮实拍赛道"调的，
套到"暗色离线图"上必然崩。所以它被单独放进 `scut_port.c` 并附上这段证据 ——
用户换图集时可以直接照着调。

### 问题二：「返回的图像应该是彩色图像吧，为什么变成灰度了？」

用户指出的现象是**对的，而且比看起来严重**。

**根因**在核心的合成阶段：`scut_composite_overlay()` 原来写的是
`dst_row[x] = scut_luma(r, g, b)` —— 把彩色标注按 BT.601 折算成一个灰度值，
因为输出缓冲当时是**单通道** `scut_u8 output_image[H][W]`。

**为什么不能只改合成、保留单通道输出**：折算值是
红→76、绿→150、蓝→29、青→179。数值确实不同，但在**暗色底图**上
这些值全部落进同一个低区间，肉眼根本分不出哪个是标注、哪个是原始像素。
于是表现就是"我明明画的是彩色，画面却是灰的，而且看不出画没画对"。

**决定：整条输出链路改成真彩色**（用户："彩色肯定是要加的，具体路径你仔细权衡一下，当断即断吧"）。
推翻的原注释理由是"车载 IPS 是灰度屏，彩色在真屏上看不出来，所以要折成灰度以保证
仿真与硬件一致"。**这个理由不成立** —— 车载是灰度屏，但那是**显示层**的属性；
算法读到的**输入图始终是灰度**（与车载完全一致，没有动），
而"显示"恰恰是最需要看清彩色标注的那一层。折成灰度只损伤显示、不带来任何一致性收益。

**改动清单（核心 → 后端 → 插件端到端）**：

- `bind/scut_bind.c`：`output_image[H][W]` → `[H][W*3]`（RGB 紧凑排布）。
- `core/src/scut_draw.c`：`scut_draw_bind()` 的**一个** `stride` 参数拆成**两个**
  （`gray_stride` 单位字节、`ovl_stride` 单位 u32 元素），
  并拆成 `s_rgb_stride` / `s_ovl_stride` 两个静态字段。
  ★ 两者不再相等，继续共用一个必然静默错位。
- `core/src/scut_frame.c`：合成改成**颜色原样写入**，删掉那段现在已不成立的折算注释；
  `scut_frame_alloc` 按 3 字节/像素分配并加了溢出校验；`scut_frame_composite` 的
  校验从 `dst_stride < w` 改成 `< w*3`，memcpy 长度同样乘 3。
- `core/src/scut_input.c`：`scut_env_seed_output_from_input` 与 `SCUT_EnvCopyOutput`
  从整块 memcpy 改成**逐像素把灰度扩成等值三通道**。
  ★ 直接 memcpy 会把灰度当 RGB 连续排，颜色全错；而按 `w*h` 拷又只填满前 1/3。
- `backends/headless/scut_headless_main.c`：`write_pgm` → `write_ppm`，
  帧名 `frame_XXXX.pgm` → `.ppm`，格式头 `P5` → `P6`。
- 插件端：`protocol.ts`（`parsePgm`/`PgmImage` → `parsePpm`/`FrameImage`）、
  `simsession.ts`、`simview.ts`、`types.ts`（`gray` → `rgb`）、
  `media/simview.js`（`drawGray` → `drawRgb`）。

**实测结果**：5 帧连续跟踪正常（`LONG_STRAI` → `LEFT_TURN`，`tracked=2`，`lost_flag=0`），
输出帧里出现**恰好 5 种非灰度颜色**：红、绿、黄、青、品红 —— 即
`camera_draw` 画的边线、中线、目标点，与 `screen.c` 的 `my_show_perspective_image()` 一一对应。

> **顺带发现的一处静默缺陷（已修）**：`scut_sched.c` 里的合成调用原来传
> `scut_composite_overlay(cmp_gray, cmp_w, ...)`，第二个参数是**目标步长**。
> 改 RGB 之后它必须变成 `cmp_w * 3`，而**漏改不会有任何提示** ——
> 合成函数那句 `dst_stride < w*3 则直接返回` 会让整帧合成被静默跳过，
> 画面是正常的底图、标注全部消失。
> 这是我第一次改完 RGB 后"颜色数仍是 0"的原因，已在代码注释里写明。

**这个自我更正的态度很好，结论本身不成立。** 我分三步查：

**第一步 —— 我的第一个 PoC 说"复现了"。这是假阳性。**

## 新发现：每帧 `malloc(80KB)` → 进程级单例

评审新提的（Low）。实情比"IDE 会话下每帧一次分配"还更没必要：
**缓冲大小从头到尾没变过**，每次都分配释放纯属浪费。

改成 `main` 里分配一次，`on_frame` 只管写。**顺带整块复杂度消失**：

```c
/* 改前：每帧 malloc/free */
vars_json = malloc(81920); malloc_ok = (vars_json != NULL);
if (malloc_ok) { ... } else { vars_json = FALLBACK_VARS_JSON; }
...
if (malloc_ok) { free(vars_json); }

/* 改后：进程级单例 */
static char *s_vars_json = (char *)FALLBACK_VARS_JSON;   /* 默认就是合法 JSON */
```

`malloc_ok` 这个标志**整个不需要了** —— 上一轮为了防止 `free` 字面量而引入的
标志，是"每帧分配"这个设计逼出来的。**设计一改，补丁就不必存在了。**

★ 但这里我先写错了一次，值得记：
我第一版收尾写成 `if (s_vars_json != (char *)FALLBACK_VARS_JSON)`，
clang 立刻报 `-Wstring-compare`：**比较字符串字面量的指针是未指定行为**
（编译器可以合并也可以不合并相同的字面量）。靠它判断 = 在赌编译器怎么实现。
于是老老实实用回独立标志 —— 和上一轮同一个教训：**所有权判断靠标志，不靠猜。**

## 轮次：2026-10-11（第七轮）配置改为工程 JSON 唯一承载 + Webview 面板

### 用户提的需求原话

> 「 Descriptive 全部丢到项目的那个json里吧，解耦，免得老出问题」
> 「我想要UI界面，能不能不删那个设置按钮，通过一个界面来配置，
>   只是存储到json里面，然后用的时候也从里面读取？」
> 「仿真环境要尽可能可以兼容所有的图片格式，用户只需要设置图片地址和格式就行了，
>   最好的情况下，甚至不用重新编译……这个插件不应该面向我的代码，
>   要考虑用户的实际需求多种多样」

### 起因（接续上一轮）

上一轮把 16 项设置分进四个子栏目（工具链/工程配置/运行期/面板与显示），
但没有解决真正的病根 —— **配置存在两个真值里**。这一轮一开始只是想修键名，
查到一半发现结构本身就是错的，于是按用户要求整个改为单一真值。

### ★ 真正的根因：contributes.configuration 的嵌套对象分组不注册内层键

0.9.3 的写法是：

```json
"scut71.toolchain": {
  "type": "object",
  "properties": { "scut71.toolchain.path": { ... } }
}
```

VS Code **只注册 `properties` 的顶层键**。所以真正注册的是一个名叫
`scut71.toolchain` 的【对象型设置】，内层 `properties` 只是 JSON Schema，不是注册项。

后果（用户三条全踩到了）：

| 现象 | 原因 |
| --- | --- |
| 设置页填了工具链路径，插件读不到 | `cfg.get('path')` 拿不到键，静默返回默认值 —— 不报错 |
| 自检报告出现「没有注册配置 scut71.toolchain.path」 | `cfg.update('path')` 直接抛错 |
| 用户为此重装了一次 VS Code | 上述两条都不指明方向 |

**判据来自用户机器上的真实报错**，不是猜的。

### 第二个病根（比第一个更隐蔽）

`project.ts` 里写着 `fromSettings ?? fromProjectConfig ?? fromLegacyConfig`，
也就是 **VS Code 设置压过工程 JSON**：

- 用户在 `scut_project.json` 里配的图集目录**根本不生效**
- 而那个设置键本身又没注册成功
- 于是【两头都落空】，还一个字都不报

这是我最该记住的一类 bug：**两份数据在互相覆盖，而每一份都可能是空的。**

### 用户关于图片格式的要求 —— 查完发现后端早就支持

用户要求"兼容所有图片格式、最好不用重编译"。没有直接动手，先去读后端：

- `scut_headless_main.c:175` 的 `pic_ext` 是【命令行选项】，
  注释写明"可逗号分隔多个"
- `pic_ext_nth()` 在 1029/1069/1508 行遍历后缀列表，逐个候选去试
- `SCUT_PIC_EXT ".bmp"` / `SCUT_PIC_DIR "pic/1"` 只是 `#ifndef` 的兜底，
  **没有写进生成的 C 代码**

也就是说这个能力一直在，只是 UI 没把它说出来。于是做了实测而非断言：

```
同一个目录交错放 0.png, 1.bmp, 2.png, 3.bmp
  --ext .png      → ['0.png', '0.png', '0.png', '0.png']
  --ext .bmp      → ['1.bmp', '1.bmp', '1.bmp', '1.bmp']
  --ext .png,.bmp → ['0.png', '1.bmp', '2.png', '3.bmp']   ← 四张全读到
```

**全程同一个 exe，一次都没重新编译。** 用户的诉求已经满足，
改动只是在 UI 提示里把它讲清楚（`pic.ext` 支持逗号分隔）。

### 实测踩到的坑：相对路径不是按 CWD 解析的

第一次测混合格式，四种 `ext` **全部失败**。没有急着下结论，去读了原始错误输出，
发现关键信息：

```
已尝试的位置：1) <exe>/../formattest  2) 工程根/formattest  3) CWD/formattest
```

相对 `--pic` 是**按 exe 自身位置反推工程根**，不是按进程工作目录。
我把 `'formattest'` 写成相对路径才全军覆没；改成 `'pic/formattest'` 立刻全通。
**判别实验的价值就在这里 —— 它逼我把错误信息读到底，而不是一句"不支持"了事。**

- 面板**不持有状态**：读 JSON → 显示 → 改完写回。关掉再开、窗口重载都不丢

**3. `scut_project.json` 扩展为 image/inputArray/outputArray/hooks/pic/run/toolchain**

优先级链反而缩短了：真值只有一处，`??` 那串也不用了。
