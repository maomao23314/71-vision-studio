### 排查结论（动手之前）

**三层现状（架构本身是对的，符合设计理念）**

```
① 插件显示层   extension/ (TS + webview)      只管 UI
        ↕ scut_project.json + stdin/stdout JSON 协议
② 仿真环境层   tools/scut_build.py + core/ + bind/ + backends/headless/
        ↕ 构建时生成的接线单元 scut_env_glue.c
③ 用户代码     code/*.c                        只有算法
```

**问题 1 根因（已确认）**

- `code/camera.c` **当前编译不过**（用 SDK 脚本实测）：
  - 第 1958 行 `camera_draw()` 用了 `image_used`（小写），该标识符不存在；正确名字是 `ImageUsed`（`Perspective.h` 里的 `#define ImageUsed *PerImg_ip`）。
  - `scut_compute_otsu_probe()` 在文件开头声明、在 `camera_report()` 里调用，**但没有定义** → 即使修好上一处，链接期也会报未定义。
  - 连带：探针编译失败 → 自动符号发现拿不到 `binary_image` → 构建脚本又报「结果图数组名在 code/ 里找不到」。
- 用户说"目前也能跑起来"= 跑的是 `.scut/bin/scut_sim.exe` 这个**旧的构建产物**，源码本身已经坏了。
- "图片明显不对"还有一层：`binary_image` 里存的是**类别值**（0/1/2/3/4/6），直接当灰度显示几乎全黑；4bb7 是把它按类别映射成颜色显示的（`screen.c` 的 `my_show_line_only`），默认视图则是**逆透视后的图 `ImageUsed` + 边线/中线标注**（`my_show_perspective_image`）。

**问题 2 根因（已确认）**

- `media/simview.css` 里 `#vars-section` 是 `display:flex; overflow:hidden`，但它的子元素 `#vars-body` **没有** `flex:1 1 auto; min-height:0`，`#vars-list` 的 `overflow-y:auto` 因为父级不受限而永远撑成内容高 → 超出部分被 `overflow:hidden` 裁掉，**滚不动**。

**问题 3 根因（已确认）**

- 后端把用户日志发到 **stderr**，行首带 `[LOG] `（`backends/headless/scut_headless_main.c` 第 2118 行）。
- 扩展 `simsession.ts` 的 `onStderr` 又在前面加了个 `[仿真] `，变成 `[仿真] [LOG] …`。
- `simview.ts` 的 `pushLog()` 用 `line.startsWith('[LOG] ')` 判断是不是用户日志 —— 前缀被 `[仿真] ` 挡住，**判定永远为假**，于是用户日志被写进「SCUT-71 构建」输出通道，而**专门的「SCUT-71 运行日志」通道和侧边栏「日志」折叠区永远为空**。
- 侧边栏 HTML 里其实有 `#log-section` 折叠块，webview 也处理 `type:'log'` 消息，但**宿主从来没往 webview 发过 `log` 消息** → 那块是死的。

**问题 4 根因（已确认）**

- `media/simview.js` 里**勾选区**已经区分了 `manual`（主动暴露，蓝色、排前面、带分组标题），但**查看区** `renderVariables()` 构造 `picked` 时把 `manual` 字段丢掉了，所以查看区所有变量长得一样。

**问题 5 根因（已确认）**

- `tools/scut_build.py` 其实已经做到"用户代码恒 `-g -O0`"（`user_flags`），真正受 `--mode` 影响的只有**环境自身**（bind 单元、核心库、后端：`env_flags` debug=`-g -O0` / release=`-O2 -DNDEBUG`）。
- 也就是说这个设置项唯一的用途是"环境库要不要优化"，而这**不该让用户选**。用户要求：C 用户代码恒 O0，其余部分可以优化。

**问题 6 根因（已确认链路可用，问题在接线）**

- 用 `tests/dap_smoke.js` 实测：`lldb-dap` + 当前 `scut_sim.exe` 的完整 DAP 会话 **6/6 通过** → 适配器与程序本身没问题。
- 插件侧疑点：
  - `package.json` 把 **`F5` 绑给了 `scut71.run`**（`when: view == scut71.simview`）。用户十有八九是**在仿真视图里**按 F5，于是触发"运行 N 帧"而不是"开始调试"，看起来就是"调试打不开"。
  - 没有独立的"调试"命令/按钮，入口只有 F5，且被上面的键位抢走。
  - 装了 `ms-vscode.cpptools`（`cppdbg`）也认 C 文件，无 `launch.json` 时 F5 可能弹调试器选择，用户容易走错。

### 问题 1：主动注册的变量看不见

**结论：两个独立的缺陷叠在一起，只修任何一个都仍然看不见。**

#### 缺陷 A：判据是错的（宿主侧）

原来的做法是"运行期注册表里的名字 − 编译期 DWARF 能看到的变量"= 手动变量。
实测证明这个判据**恒等于空集**：

- 运行期注册表 42 个，编译期 DWARF 清单 42 个，**交集也是 42**（差集 = 0）。

为什么？因为自动发现的包装单元会把用户源码 `#include` 进来，
于是用户写的**每一个** `SCUT_WATCH_SCALAR` 都同时出现在两边 —— 两边都覆盖它，差集自然为空。

更关键的是：用户手写注册的最常见形式是**结构体成员**
（`SCUT_WATCH_SCALAR("cam_err", &m7_0_data.cam_err, SCUT_T_F32)`），
而**结构体成员在 DWARF 里没有独立的变量条目** —— 实测那 7 个手写变量一个都不在 DWARF 清单里
（单 `camera.c` 只产出 32 个 DWARF 变量，合并后 42 个）。
所以"只给 DWARF 变量打标记"这个做法注定漏掉全部 7 个。

**改法：改成扫源码。**

- `tools/scut_symbols.py`：新增 `scan_manual_watches(src)`，正则匹配手写的
  `SCUT_Watch("名字", …)` / `SCUT_WATCH_SCALAR("名字", …)`，**只去注释、不去字符串字面量**
  （要抓的恰恰就是那个字符串）。名字写进清单**顶层**的 `manualWatches`。
- `tools/scut_build.py::merge_manifests`：**跨所有 TU 求并集**。
  只看单个文件的话，注册写在哪个文件会决定这个功能有没有效 —— 结果取决于无关因素。
- `extension/src/build.ts`：把运行期独有的条目（`extra`，也就是 DWARF 覆盖不到的那批）
  按 `manualWatches` 标记，而不是一律当自动捕获。
- **排序**：手动项要先挑出来置顶（`[...manual, ...extra.filter(manual), ...auto, ...extra.filter(自动)]`）。
  只拼一次的话，那 7 个结构体成员会落到列表最后 —— 而它们恰恰最该置顶。

#### 缺陷 B：注册函数压根没被调用（工程侧）

`camera_watch()` 里写着那 7 行注册，但这个函数**从来没被执行过**：
既不在 `scut_project.json` 的 hooks 里，也不在生成的接线单元里 —— 全仓库只有"定义"和"声明"，没有调用。
所以那些变量从来没有被注册进运行期注册表（实测注册表 42 个，不含这 7 个；挂上钩子后变成 49 个）。

**改法**（用户拍板："丢进 init 函数里面，这样也会自动调用"）：
在 `集成仿真环境测试/scut71-project/scut_project.json` 的 `hooks.init` 里追加 `camera_watch`。

#### 附带修掉的显示层崩溃

- `extension/media/simview.js::varMeta()` 原来写的是 `(v.kind || '').replace('SCUT_T_','')`。
  `kind` 在两个来源里**类型不同**：编译期清单给字符串 `"SCUT_T_I32"`，运行期注册表给**数字**。
  数字走 `.replace` 直接抛 `TypeError`，而它是在渲染**整个变量列表**的循环里抛的 ——
  于是变量面板整块空白，连已经渲染好的部分一起没掉。
  改成 `String(v.kind == null ? '' : v.kind).replace(...)`。
  **这个是本轮测试真正抓到的**（见下面"测试"一节）：浏览器里只显示跨源的 `Script error.`，
  拿不到行号，最后是用 Node + DOM 桩复刻出来的。
- `extension/src/simview.ts::sendSnapshot()`：过滤条件从"只看逐条目的 manual 标记"
  改成"以 `manualWatches` 为准 + 条目标记兜底"，与 `build.ts` 同源。

### 问题 3：逆透视是不是跑了两次

**结论：没有。环境是对的，不是重复调用初始化。**证据如下：

1. **探针实测**：在用户代码里打印调用次数，跑 3 帧 → `[PROBE] camera_init #1`，
   `ImagePerspective_Init()` **只出现一次**。
2. **bench 路径排除**：帧 JSON 里前两帧 `bench=False`，说明没走 `--repeat` / `b<N>` 那条重复路径。
3. **静态检查**：`ImagePerspective_Init();` 全工程只有**一个**调用点（`camera.c:2150`，在 `camera_init` 里）；
   生成的接线单元里 `ENV_REGISTER(SCUT_ROLE_INIT, …)` 也只有**一个**。
4. `core/src/scut_sched.c` 里 `s_init_ran` 保证 INIT 恰好执行一次。
5. **画面佐证**：输入在上、输出在下的对比图，输出呈现梯形道路边 + 黑色四角 ——
   这是**一次**逆透视的典型特征；跑两次会是明显的双重形变。

**唯一"每帧跑两遍"的东西是 `scut_compute_otsu_probe()`**（由 `camera_report` 调用，
读一遍 `mt9v03x_image` 统计 256 桶直方图）。但那是**直方图统计**，不是第二次透视变换，
而且放在**不计时的 DRAW 阶段**。`camera_draw` 还会把 `ImageUsed[i][j]`（透视视角的图）
逐像素写一遍 —— 也是一次全图写，但同样只做一遍。

> 如果用户仍觉得"跑了两次"，那多半是**看到输出图的边线被画了两遍**（`camera_draw` 的标注 +
> 算法本身的结果图叠加），而不是算法被执行了两次。下次可以看「计时」栏：真跑两次的话
> `processUs` 会翻倍。
