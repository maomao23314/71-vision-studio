### 关于第 4、5 项：是怎么验证的

**调试（第 5 项）**——我没有只测"能编译"，而是**直接以 lldb-dap 为子进程走了一遍完整 DAP 协议**
（`initialize → launch → setBreakpoints → configurationDone → stopped → threads/stackTrace/scopes/variables → continue → exited → disconnect`），
这与 VS Code 内部做的事完全一样，只是没有 UI 外壳。结果：

```
PASS  命中断点（stopped 事件）
PASS  调用栈里能看到用户代码
        栈顶: my_process  @ main.c:126
PASS  scopes 返回作用域
        在作用域 "Globals" 里看到: g_left_line = int[120] @ 0x7ff65807e150
PASS  程序正常结束（exited 事件）   退出码: 0
15 passed, 0 failed
```

**Webview（第 4 项）**——DOM 无法从扩展宿主断言（沙箱）。我的做法是：
从 `simview.ts` **抽出真实的 HTML 外壳**，配上真实的 `simview.js` / `simview.css`，
在无头 Chromium 里加载，用一个桩替掉 `acquireVsCodeApi()`，然后**喂进真实的 PGM 帧数据**，
最后截图 + 读回画布像素。截图见 `docs/proof_webview.png`，可以看到：
帧图像、`THRE 75 / LOST 0` 文字、计时读数、工具栏、4 个变量勾选框、
真实数值、截断提示、以及两条由数组数据画出的曲线。

剩下唯一没覆盖的只有"VS Code 宿主本身"（即 webview 容器、CSP 注入、消息桥）。

### 验证过程中我自己的测试写错了三次（记录下来避免重犯）

| 错误 | 症状 | 真相 |
|---|---|---|
| 只加载 JS+CSS，没给 HTML 外壳 | canvas 数量 0，但能发出 `ready` | `simview.js` 是按 id 绑定 `simview.ts` 生成的元素的，必须给真实外壳 |

## 三、本轮发现并修复的真实缺陷

> 全部是**静默失败**——不崩溃、不报错，只是结果悄悄错掉。
> 这正是本项目立项要消灭的那一类问题。

| # | 缺陷 | 症状 | 发现方式 |
|---|---|---|---|
| 1 | **绘制被静默丢弃** | 调度器从不合成覆盖层，用户所有标注不出现 | 子代理对 `scut_frame_composite` 无人调用做了静态核查 |
| 2 | **第 1 帧整帧变黑** | 覆盖层是 `static`（全 0），而 `0` 是合法黑色、不是"透明"哨兵 | 修复 #1 后由子代理用反事实实验测出 |
| 3 | **图集从不加载** | `--pic` 解析了却没人调用解码器，算法在全零图上跑 | 我自己核对 `s_histogram` 全堆在第 0 桶 |
| 4 | **`img` 字段生成非法 JSON** | Windows 路径的 `\f`、`\d` 被当转义符，插件解析整行失败 | 子代理顺带指出 |
| 5 | **核心库从不重建** | 构建脚本假定库已存在；改了核心源码却跑的是旧库 | 我查 mtime 发现库比源码旧 |
| 6 | **`pic` 字段被解析器丢弃** | 仿真发了"这帧用的哪张图"，插件侧丢掉 → 界面永远显示第一张 | 我写 Node 级测试时发现 |
| 7 | **指针值被当数字** | `Number('0x4050b0')` 合法 → 给指针画出一条无意义曲线 | 我写测试时发现 |
| 8 | **编译入口缺后端** | 从不编译后端 → `undefined symbol: WinMain`（报错完全不提"少了个后端"） | 端到端首次构建 |
| 9 | **DWARF 5 静默全空** | 用户加 `-gdwarf-5` → 0 个变量、退出码仍为 0 | 我实测 + 加了显式检测 |
| 10 | **暂停/自检正则锚定错误** | `^` 未加 `MULTILINE`，整输出 `search` 恒假 → 把正常结果误判为失败 | 回归测试当场抓住 |

### 其中值得单独说的三条

**缺陷 2（第 1 帧全黑）**：`static scut_u32 s_overlay[H][W]` 被零初始化，
而 `0x00000000` 是**合法的黑色**，不是"无标注"哨兵 `0xFFFFFFFF`。
合成一接上，整帧就被涂黑。症状是「第 1 帧黑、第 2 帧起正常」，
极容易被误判成"初始化没跑"而查错方向。
我在 `bind` 里用构造函数填哨兵修掉了根因
（注意：**不能**用 `= {{0xFFFFFFFFu}}`——C 会把其余元素补 0，实测 12 个里只有 1 个生效）。

**缺陷 5（核心库不重建）**：这条最隐蔽——我一度以为合成修复没生效，
实际是构建脚本一直在链接**旧库**。已加入基于 mtime 的增量重建：
源码比库新才重编，因此"改算法不重编环境"的收益仍然保留。

**缺陷 10**：修 DWARF 兼容性时我给正则加了 `re.MULTILINE` 之外还写了
"整输出是否含任何 DIE"的自检，但 `^` 在无 `MULTILINE` 时只匹配字符串开头，
导致自检把**一切正常**的输出判为失败。是项目自带的回归测试当场抓住的。

## 五、明确的已知边界

1. **未在真实 VS Code 窗口里人工点开过面板**。
   第 4、5 项已用真实 Chromium 与真实 DAP 协议分别验证了各自的**逻辑与渲染**，
   但"VS Code 宿主本身"（webview 容器、CSP 注入、消息桥、F5 触发）仍未走过一遍。
   这是当前唯一剩余的验证缺口。
2. **PNG/JPEG 不支持**，只认 BMP。核心已留 `SCUT_FRAME_ERR_UNSUPPORTED_FORMAT`
   与集成点，`stb_image` 是后续工作。
3. **中文文字不支持**：内置 8×8 ASCII 字库，中文渲染为占位方框。
4. **两个覆盖层缓冲并存**：`bind` 的静态数组（绘制实际写的）与
   `frame` 模块堆分配的那个（当前无人写）。合成走前者。
   这是历史遗留的重复，**属于潜在陷阱**，应后续收敛为一个。
5. **`INIT` 阶段无法用访问器读输入图**（阶段门控只放行 `PRE_FRAME`/`PROCESS`）。
   直接访问全局数组仍可行，但推荐在 `PROCESS` 里读。
6. **仿真 ≠ 真机性能**：默认 `-O0`；`--mode release` 给 `-O2` 作对照。
7. **QEMU 确定性计时未实现**（按决策 D-8 只保留扩展点）。
8. **调试时断点若下在循环体内会频繁命中**——这是调试器的**正确**行为，
   不是缺陷（实测确认：lldb CLI 下连续 6 次 continue 得到 6 次命中）。
   但初次使用的人容易误以为"卡住了"，值得写进用户文档。

## 六、按设计理念自检

| 理念 | 本轮落实 | 反例（如有） |
|---|---|---|
| **上手即用** | 核心库自动构建；工具链自动探测；错误信息全部是「原因 + 下一步」的中文；图集缺失时明确警告而不是给一张黑图让人猜 | 首次构建需 1.5 s（可接受） |
| **代码松耦合** | 核心不依赖任何图形库（headless 已验证）；呈现后端只提供 `main`；`config` 只影响 bind 单元 | 两个覆盖层缓冲是耦合残留 |
| **适应任意用户代码** | 构造函数自注册 + 角色 + 显式优先级；自动发现覆盖到 `static`；函数可放任意文件 | 未被引用的 `static` 会被编译器删除（C 语义，非缺陷） |
| **模拟单片机** | `code/` 只依赖 `scut_sdk.h`；绘制/日志是主机侧设施，车载可给空实现 | 尚未做真实交叉编译验证 |
